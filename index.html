Resumo

O DevClash é uma aplicação web educacional desenvolvida para apoiar a revisão de conhecimentos relacionados a SQL, PostgreSQL, modelagem de dados e temas de tecnologia. O sistema apresenta perguntas de múltipla escolha, cronômetro, pontuação variável, explicações após cada resposta e classificação dos participantes. A solução utiliza HTML, CSS e JavaScript no frontend; Node.js e Express no backend; e PostgreSQL para armazenar perguntas, jogadores, partidas e respostas. Sua modelagem relacional distribui as informações em sete tabelas, com chaves e restrições destinadas a manter a consistência dos dados. Este artigo documenta a implementação descrita nos materiais técnicos do projeto, incluindo funcionamento, estrutura, integração, implantação e limitações identificadas.

Palavras-chave: DevClash; quiz educacional; JavaScript; Node.js; PostgreSQL; modelagem relacional; API REST.

1. Introdução

A aprendizagem de conteúdos técnicos exige prática frequente e retorno claro sobre os erros. Em temas como linguagem SQL e bancos de dados, a resolução de questões pode ajudar a identificar dificuldades e consolidar conceitos. O DevClash foi desenvolvido com essa finalidade, transformando exercícios de revisão em uma experiência interativa.

Além da proposta educacional, o projeto demonstra como integrar componentes de uma aplicação web: a interface apresentada ao usuário, a lógica de uma API HTTP e um banco de dados relacional. O jogador interage pelo navegador, enquanto o servidor consulta perguntas e registra resultados quando a conexão está disponível.

2. Objetivos do projeto

2.1 Objetivo geral

Desenvolver um quiz web para exercitar conhecimentos de tecnologia, corrigir respostas, calcular pontuações e apresentar o desempenho dos jogadores.

2.2 Objetivos específicos

  • Disponibilizar perguntas objetivas organizadas por categoria e dificuldade.
  • Aplicar limite de tempo e fornecer explicação após cada resposta.
  • Registrar jogadores, partidas e respostas em um banco PostgreSQL.
  • Exibir um ranking baseado na melhor partida de cada jogador.
  • Manter perguntas locais como alternativa em caso de indisponibilidade da API.
  • Oferecer uma interface responsiva com o mascote Claudinho.

3. Metodologia de desenvolvimento e documentação

O projeto foi organizado em três componentes: frontend, backend e banco de dados. As telas e a interação foram construídas com tecnologias web nativas; a API foi estruturada com Express; e o modelo de persistência utiliza tabelas relacionais do PostgreSQL.

Este artigo foi elaborado a partir dos documentos Documentação completa do projeto e Documentação completa do projeto — DDL e DDM. Os dados apresentados se referem à versão descrita nesses materiais. Eles foram produzidos a partir da inspeção do código e não comprovam, por si só, testes completos no ambiente de produção.

4. Arquitetura do sistema

A aplicação separa as responsabilidades entre a interface web, a API e a base de dados. O frontend exibe as perguntas, controla o tempo, calcula os pontos e apresenta a experiência visual. O backend recebe requisições HTTP, valida dados e utiliza o pacote pg para acessar o PostgreSQL.

Navegador (HTML, CSS e JS)→ API (Node.js e Express)→ PostgreSQL

Quando o serviço remoto de perguntas não responde, o frontend pode carregar questões locais presentes em js/questions.js. O ranking local é mantido temporariamente com sessionStorage; a preferência de áudio utiliza localStorage.

FrontendHTML5, CSS3 e JavaScript
BackendNode.js e Express
DadosPostgreSQL e SQL

5. Funcionamento do DevClash

O participante informa um nome de até 20 caracteres e inicia o quiz. A versão analisada pelos documentos reúne 45 questões, das quais 5 são identificadas como bônus. As questões são preparadas e apresentadas por dificuldade, com alternativas embaralhadas. A sinalização de bônus não adiciona um multiplicador de pontos.

Cada pergunta tem 50 segundos. Após a confirmação de uma resposta, o sistema informa o acerto ou erro, apresenta uma explicação e disponibiliza a fonte correspondente. Ao fim da partida, mostra os totais e tenta registrar o resultado no servidor.

5.1 Regras de pontuação

Tempo restante ao acertarPontuação
40 segundos ou mais10 pontos
De 35 a menos de 40 segundos8 pontos
De 25 a menos de 35 segundos6 pontos
De 15 a menos de 25 segundos4 pontos
Mais de 0 e menos de 15 segundos3 pontos
Resposta incorreta1 ponto
Tempo esgotado0 ponto

A pontuação máxima teórica de uma rodada com 45 questões é de 450 pontos. O ranking remoto considera a melhor partida de cada jogador; no desempate, prioriza o menor tempo total e, depois, a partida mais antiga.

5.2 Mascote Claudinho

O mascote Claudinho participa da experiência por meio de expressões, reações e mensagens relacionadas aos eventos do jogo. A documentação também descreve a reprodução opcional de clipes de áudio em MP3, com controle de preferência pelo usuário.

6. Modelagem do banco de dados

O banco do DevClash utiliza o PostgreSQL e possui sete tabelas. Sua estrutura pode ser dividida em dois conjuntos: conteúdo do quiz (categorias, fontes, questões e alternativas) e histórico do usuário (jogadores, partidas e respostas).

TabelaPrincipais camposResponsabilidade
categorias_perguntasid, nomeOrganizar os temas das questões.
fontesid, nome, urlGuardar referências das explicações.
questao_quizid, categoria_id, pergunta, explicacao, dificuldade_pergunta, fonte_id, pergunta_bonus, ativoArmazenar enunciados e características das questões.
opcoes_perguntasid, id_pergunta, posicao_pergunta, alternativas, esta_corretoRegistrar alternativas e indicação de resposta correta.
jogadoresid, nome, criado_emIdentificar participantes pelo nome.
dados_partidasid, jogador_id, nome_jogador, pontuacao_total, tempo_totalGuardar o resumo de cada partida.
registro_perguntasid, id_partida, pergunta_id, posicao_selecionada, status, pontos, tempo_gastoGuardar cada resposta, o tempo e a pontuação.

Os relacionamentos principais seguem a cardinalidade um-para-muitos (1:N): uma categoria pode conter várias questões, uma questão pode possuir várias alternativas e um jogador pode ter várias partidas. A tabela registro_perguntas conecta as respostas às partidas e às questões.

7. Integridade referencial e normalização

O modelo utiliza chaves primárias (PRIMARY KEY) para identificar registros e chaves estrangeiras (FOREIGN KEY) para ligar as tabelas. Restrições NOT NULL, UNIQUE e CHECK controlam valores obrigatórios, unicidade e limites permitidos.

  • UNIQUE (id_pergunta, posicao_pergunta) impede duas opções na mesma posição dentro de uma questão.
  • Um índice único parcial permite no máximo uma alternativa marcada como correta por questão.
  • UNIQUE (id_partida, pergunta_id) impede registrar a mesma questão duas vezes na mesma partida.
  • Uma chave estrangeira composta verifica se a opção escolhida pertence à questão respondida.
  • ON DELETE CASCADE remove opções quando a questão é excluída e remove registros quando a partida é excluída.

A separação das entidades reduz duplicações e facilita a organização dos dados. Entretanto, a documentação identifica informações redundantes: dados_partidas.nome_jogador repete o nome do jogador, enquanto questao_quiz.nome_fonte e questao_quiz.url_fonte repetem dados da tabela fontes. Por isso, não se deve afirmar que o esquema inteiro satisfaz rigorosamente a terceira forma normal sem uma análise adicional.

8. API HTTP e consultas SQL

A API utiliza JSON para a comunicação com o navegador. Entre suas responsabilidades estão carregar perguntas, receber resultados, consultar o ranking e verificar a conexão com o banco.

MétodoRotaFinalidade
GET/api/healthVerificar disponibilidade da aplicação e do PostgreSQL.
GET/api/questions?limit=45Obter questões ativas para a partida.
POST/api/matchesValidar e registrar uma partida.
GET/api/ranking?limit=10&player=NomeConsultar as melhores partidas e a posição do jogador.

8.1 Exemplo de DDL

O comando CREATE TABLE é utilizado no script schema.sql para definir as tabelas e suas regras. O exemplo abaixo corresponde à definição da tabela de jogadores descrita na documentação:

CREATE TABLE IF NOT EXISTS jogadores (
  id        SERIAL PRIMARY KEY,
  nome      TEXT NOT NULL UNIQUE
            CHECK (char_length(nome) BETWEEN 1 AND 20),
  criado_em TIMESTAMPTZ NOT NULL DEFAULT now()
);

8.2 Exemplos de SELECT

As consultas abaixo ajudam a verificar o conteúdo armazenado e os resultados das partidas:

-- Contar questões cadastradas e sinalizadas como bônus
SELECT COUNT(*) AS total,
       COUNT(*) FILTER (WHERE pergunta_bonus) AS bonus
FROM questao_quiz;

-- Conferir quantidade de alternativas por questão
SELECT q.id,
       COUNT(o.id) AS alternativas,
       COUNT(*) FILTER (WHERE o.esta_correto) AS corretas
FROM questao_quiz q
LEFT JOIN opcoes_perguntas o ON o.id_pergunta = q.id
GROUP BY q.id
ORDER BY q.id;

-- Consultar as dez partidas mais recentes
SELECT id, nome_jogador, pontuacao_total,
       tempo_total, terminou_em
FROM dados_partidas
ORDER BY terminou_em DESC
LIMIT 10;

Para montar o ranking remoto, a implementação documentada utiliza DISTINCT ON (jogador_id) para selecionar a melhor partida de cada participante e ROW_NUMBER() para calcular as posições.

8.3 Gravação das partidas

Na rota POST /api/matches, o servidor valida nome, identificadores de questões, respostas, status, pontuação e tempo informado. A gravação utiliza uma transação para salvar jogador, partida e registros de respostas em conjunto. Em caso de falha, a transação pode ser revertida com ROLLBACK, evitando registros parciais.

9. Infraestrutura e hospedagem

No ambiente de hospedagem informado pela equipe, o frontend fica no GitHub Pages, o backend Node.js/Express é executado no Render e o banco PostgreSQL é gerenciado pelo Supabase. Essas plataformas desempenham funções distintas na aplicação.

PlataformaResponsabilidade
GitHub PagesPublicação dos arquivos estáticos HTML, CSS e JavaScript.
RenderHospedagem da API Node.js/Express.
SupabaseHospedagem e gerenciamento do banco PostgreSQL.

A interface faz requisições ao endereço público da API. O servidor recebe essas solicitações e acessa o banco com as credenciais definidas em variáveis de ambiente, sem disponibilizar a senha de conexão no JavaScript do navegador. A documentação técnica inclui um arquivo render.yaml e descreve as variáveis DATABASE_URL, DATABASE_SSL, CORS_ORIGIN e PORT.

10. Segurança, acessibilidade e limitações

Entre os cuidados registrados na versão documentada estão consultas SQL parametrizadas, validação de entradas recebidas pela API, limite do corpo JSON e uso de transações no armazenamento. A interface apresenta componentes nativos, mensagens de feedback e regras CSS para telas menores e redução de animações.

Existem, contudo, limitações importantes. O nome do jogador não é uma autenticação, a API expõe o campo correctAnswer ao cliente e o servidor não recalcula integralmente a pontuação a partir de um cronômetro confiável. A versão descrita também não inclui uma proteção específica contra excesso de requisições. Essas condições não impedem o uso educativo, mas exigem atenção caso o ranking seja usado em competições com necessidade de impedir trapaças.

Limite da análise: os PDFs registram verificações de código e propõem testes funcionais. Eles não comprovam a execução de todos esses testes com o banco remoto em produção. Alterações feitas depois da versão documentada precisam ser verificadas no código atual.

11. Considerações finais

O DevClash reúne recursos de aprendizagem interativa com conceitos fundamentais de desenvolvimento web e bancos de dados relacionais. A divisão entre interface, API e PostgreSQL permite demonstrar a comunicação entre camadas, enquanto a organização em sete tabelas evidencia o uso de chaves, relacionamentos e restrições de integridade.

Além de apresentar questões e resultados, o projeto serve como exemplo prático de persistência de dados, execução de consultas SQL, tratamento de respostas HTTP e utilização de um banco relacional. Os pontos de melhoria identificados mostram oportunidades de evolução sem descaracterizar a proposta inicial: oferecer uma ferramenta acessível para revisar conhecimentos técnicos de maneira dinâmica.
